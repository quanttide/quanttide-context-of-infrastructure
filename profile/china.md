# 微服务托管选型：FC 与 ACK Serverless

## 现状与矛盾

量潮的微服务群托管在阿里云函数计算（FC），两个矛盾同时存在：

- **冷启动叠加**：调用链上多个服务同时冷启动，延迟逐级累加；
- **最小实例成本高**：为消除冷启动给每个服务开最小实例，常驻费用线性叠加，反而比 K8s 更贵。

FC 的最小实例，本质是用 Serverless 的单价买常驻服务器，通常不划算。

## 方案对比

| 方案 | 成本特点 | 冷启动 | 运维 |
|:--|:--|:--|:--|
| FC + 最小实例 | 按量单价高，多服务常驻成本叠加 | 可消除，但代价高 | 几乎为零 |
| 传统 K8s | 包年包月节点摊薄，服务越多越便宜 | 无 | 有集群运维成本 |
| ACK Serverless | 按秒计费，可缩容到 0，无固定管理费 | 默认有，可配常驻 | 低，接近 Serverless |
| ACK Knative + 保留实例 | 低规格实例保活，按需拉起标准实例 | 首个请求无冷启动 | 较低 |

## 关键发现

- ACK Serverless（ASK）没有强制常驻 Pod，可缩容到 0，只为实际消耗的 ECI 资源按秒付费。
- Knative 保留实例是解冷启动的关键：无流量时留一个低规格热实例，成本远低于 FC 最小实例；请求到达即由它承接，同时并行拉起标准实例；流量切换后保留实例自动下线。

## 初步建议

满足以下多数条件时，建议从 FC 迁往 ACK Serverless + Knative：

- FC 账单中最小实例常驻占比超过 30%；
- 微服务数量 ≥ 3，且核心服务对冷启动敏感；
- 流量有波峰波谷，希望闲时缩容、忙时弹性；
- 团队能接受轻量 K8s 运维，或愿意使用 ACK 托管能力。

配置思路：

- 核心链路服务：开 Knative 保留实例，低规格（如 1C2G 或突发性能实例）保活；
- 非核心与低频服务：缩容到 0，完全按需；
- 标准实例：按实际 QPS 自动弹性，按秒计费。

## 决策前要核算的数据

1. 当前 FC 月账单中最小实例费用是多少；
2. 微服务数量与每个服务的规格（vCPU／内存）；
3. 流量曲线：全天候高位，还是有明显波峰波谷；
4. ACK Serverless 侧预估：保留实例常驻成本、弹性实例按量成本，以及可能的 SLB／NAT 等费用。

判断式：`FC 最小实例月费 > ACK Serverless 保留实例 + 弹性预估月费 + 可接受的运维投入`，成立则迁移更优。

## 注意

- 保留实例持续计费，但规格低，成本可控；
- 用 ECI 保留实例需安装 ACK Virtual Node 组件；
- 保留实例规格应低于服务正常规格，只用于承接首个请求；
- 计费以阿里云官网最新价格为准。

## 结论

需要的不是 FC 的最小实例，而是 ACK Serverless + Knative 保留实例：用低规格热实例解决冷启动，用弹性按量控制成本。

## 归类（按元认知骨架）

- 触发点：FC 冷启动叠加与最小实例常驻成本；
- 方法：迁 ACK Serverless + Knative 保留实例（低规格保活、标准实例弹性）；
- 价值：延迟体验与成本可控；
- 排除的形态：FC 最小实例常驻；
- 关系：触发点 —应对→ 方法 —服务于→ 价值 —排除→ 排除的形态。

情绪层与二阶层（表达）无对应条目——属提取粒度还是框架缺格，待判。
